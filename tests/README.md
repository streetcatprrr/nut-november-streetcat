# Tests

All tests run against a local Nutshell mint with a fake Lightning backend (no real money):

```
pip install cashu
MINT_BACKEND_BOLT11_SAT=FakeWallet MINT_PRIVATE_KEY=test MINT_DATABASE=./data/mint FAKEWALLET_BRR=TRUE MINT_INPUT_FEE_PPK=0 \
  python3 -m cashu.mint --port 3338 --host 127.0.0.1
```

On Python 3.13, `pip install cashu` (0.21.0) needs a hand: install its dependencies with `breez-sdk-spark==0.18.0`, `limits<4` and `marshmallow<4`, a `coincurve` 21 wheel, then `bip32` and `cashu` with `--no-deps`.

What "passes" means here (audit of 10 Nov). There is no runner and no CI: each file is run by hand, or one after another by a loop that reads each one's exit code. Most suites count their checks and exit 1 when one fails. Seven only print what the page said and fail only if something throws: `browser_test`, `keys_test`, `library_test`, `release_test`, `status_test`, `lightning_test`, `offline_test`; their output has to be read. `core_test` and `publish_test` counted their checks and still exited 0 until 10 Nov. The browser suites pin their own Streetcat keys next to the published one (`pin.mjs`), tap where the app asks to hold, and keep the moving texts still, so they do not run those three things as shipped; `signed_test`, `trust_test`, `audit_test`, `hold_test` and `anim_test` are the ones that do.

- `library_test.mjs` — the flow with cashu-ts only (`npm i @cashu/cashu-ts && node tests/library_test.mjs`).
- `browser_test.mjs` — the real page in Chromium, three parties with separate storage (`python3 -m http.server 8080 --directory app`, then `node tests/browser_test.mjs`; needs `playwright` and a `tokens.json` with two plain tokens from the local mint, see the top of the file).
- `status_test.mjs` — the status page: four real donations through `index.html` (one released, one left locked, one refunded, one left past its deadline) and one forged ledger entry, then `status.html` must report each from the mint alone. Then, in the donor's own browser, the page must list those four donations by itself and turn them into ledgers that read back the same. Same server as above; it mints its own fake ecash.
- `lightning_test.mjs` — donating with Lightning: the mint check on a new campaign, an invoice paid and minted straight into the lock, a reload between payment and minting (the mint call is blocked, then the page reloads), the mint's answer lost after it minted (the page gets the ecash back with NUT-09 restore), a link with a bad deadline, release with its answer lost (restored at once; and once more with restore blocked too, finished when the page is reopened), a refund paid to a Lightning invoice, a too-large invoice refused before anything moves, and a closed campaign. The fake Lightning backend pays the mint's own invoices, so no wallet is needed.

- `keys_test.mjs` — keys are never lost: a clinic that makes a new key (in its settings) after donations were locked to the old one can still sign them (the old key is kept; the signing is done in the page, as "Certify a token" did before it was removed on 12 Nov); a browser holding another clinic key signs nothing; importing an export keeps the keys that browser had; the Streetcat tab of a browser without the Streetcat key stops before asking the mint; and a new key that cannot be saved changes nothing.

- `release_test.mjs` — Streetcat releases only what the clinic really certified: a token with one proof unsigned ("Partly signed (2 of 3) — not certified") or signed with another key ("Signed with a key that is not MOCHI's clinic key") is refused before anything is sent to the mint; a part the donor already took back after the deadline is left out of the release; the clinic's key can still sign after the deadline (done in the page, as the removed "Certify a token" did); and the status page counts each proof once, however many ledger entries list it (a part of a donation, the donation, and its certified copy). Once released, the button says so in Streetcat's green ("✓ Released") and cannot be pressed again, and the page buzzes (counted through `navigator.vibrate`); "release another token" empties the box and brings the button back; the same token pasted again says "✓ Already released" before anything is pressed, with no swap sent.
- `offline_test.mjs` — signing without coverage: the clinic opens the app once with a connection, then its server is switched off and the browser goes offline. The app must still open from its service worker (`app/sw.js`), with its font, read the donation with the mint's keys kept from last time, and sign it (in the page, as the removed "Certify a token" did); back online, Streetcat releases it. The cat recognition, got ahead of time with Offline setup's button (without starting it), must load offline from the phone and give, for a drawn photo, the numbers Streetcat's phone gives; a donor's phone, which never asked for it, must keep none of its 121 MB.
- `sw_test.mjs` — the service worker's version: `app/sw.js`'s BUILD must be the hash of the files it keeps, of itself and of `vercel.json` (its headers stay with each version's cached responses; `tools/stamp-sw.mjs`); fails when a file changed and the stamp was not run, or a file it keeps is missing. No browser. Since 10 Nov it also fails if anything of the demo build (branch `dest-demo`: `demo.js`, a key taken for Streetcat's that is not the pinned one, a test mint's address) is in `app/`, if a page loads a script outside its known list, or if the pinned key is not the published one.
- `swupdate_test.mjs` — a new version as a phone gets it (review of 9 Nov), on a copy of the app served on port 8096 with the service worker on: the first version is taken at once; version 2 is published and the app, just opened with nothing under way, opens again in it, every file from one cache filled whole, and Keys says its version (`Version <stamp>`); offline it still opens; version 3 is published while a payment waits for the mint: the app stays on version 2, and takes version 3 once nothing is under way, back in front; version 4, with one of its files missing, is never used and leaves no cache behind. Then, as every phone that has the app gets this version: the service worker before it (`sw-v6.fixture.js`, network first, its copy in `streetcat-app-v6`) serves the app on port 8097; this version is published over it, and the page takes the new worker and opens again in it, every file from its own cache, the old copy deleted; offline it opens as this version.
- `timing_test.mjs` — deadlines (plan step 1), in the three apps against the local mint and two local relays (7271/7272): two pots of one partner, refunds in 2 and in 30 days; a request for work in 5 days from the first says the dates, then in red that refunds open before the work, the funding checked at the mint in green, "Send anyway", and offers only the other pot ("Pay from … · refunds from …"), where it is ✓; with the mint not answering Rescue's phone, "✗ Funding not checked · Last verified at …", sent anyway and saying so to the partner, whose app asks the mint itself; refunds open too and no answer: not sent (the page's clock moved past the deadline); Donate shows the invoice's own expiry, and the mint's quote's only when it differs (the payment held back). Screens at 320–430 px; `SHOT_DIR` for t1–t4.
- `repeat_test.mjs` — repeat and drafts (plan step 2), Rescue and the partner's app against the local mint and two local relays (7281/7282): a request confirmed and released; `Repeat request` opens New request saying where it comes from, with its pot and what it is, and without its cat, photos, cost, date, note or donations (`Last time: 50 sat on … · check the cost`); without a date it is not sent; sent, a new id that says `Repeated from R-…`, the old one released and unchanged, none of its proofs taken; `Repeat a recent one`; `Keep as draft` on the kind's screen, reserving nothing, back in the form, and `Delete draft`; with the pot closed (the page's clock moved), `✗ … closed on …. Choose another pot.` and `Make a campaign`. Screens at 320–430 px; `SHOT_DIR` for p1–p4.
- `core_test.mjs` — `app/core.js` in Node with the app's own cashu-ts bundle (no browser): keys derived from a campaign key, DON- codes, packing for link/file/relay (and a link that would expand without end), the request (with the cat's photos as caught, and what is not a valid list of them: four, a slot twice, a bad SHA-256, one too big; their parts, which rebuild each photo and name the clinic's key) and the clinic's answer with every way it can be wrong (one proof unsigned, another key, a declaration changed afterwards or for another request, a signed report), a release where one proof is split and its rest goes back under the same lock, the donor finding that rest with NUT-09 restore and taking it back after the deadline, the ledger v2 with the clinic's declaration, and a volunteer's acknowledgment. Run it with `MINT=http://127.0.0.1:3339` too (fees are paid out of Streetcat's part; the rest stays exact). Also the deadlines' date rule (plan step 1): a day with no hour ends at the end of that day in Madrid, the hour changes of March and October, the four levels from each proof's own lock, the days to confirm and the margin, a leftover of a partial release and two pots one second apart; and an invoice's own expiry (BOLT 11) against the mint's quote. Who received a delivery: only a salted fingerprint in the declaration (none in a ledger made from it), the line read back only when it gives that fingerprint, one changed on the way not shown.
- `relay_test.mjs` — `app/relay.js` (requests and answers by Nostr relay) against three local test relays from `nostr_relay.mjs` (one refuses every event); needs Node 22 and `npm i ws` (for the test relays only), no mint. Streetcat sends a request and two relays confirm it; the clinic receives it once; its receipt and certified answer come back; an answer that comes before its request is known in that browser is not dropped, and comes (once) when the request is there; a request or an answer from a key that is not the campaign's is dropped, and so is a message for another clinic; with every relay down the message waits in the outbox and goes out when they are back; and the relays hold nothing readable (no cat, campaign, spending key or proof, and every wrap is signed by a throwaway key); the outbox keeps a message's copy only while it waits (once sent, only how it went, the last 300), cuts down an outbox from before at its next save, says so when the phone has no room left (`NO_ROOM`), and keeps a message added while it is sending (it was overwritten with the list read first). Relays slow to confirm (`nostr_relay.mjs` options `okDelay`, `storeDelay`, `mute`; 8 Nov, nostr.mom confirmed half a minute late and nos.lol never): one that keeps a message but confirms late counts as having it (asked by its id), one that has not kept it yet or never answers does not, one that answered no is believed, one not reached was never sent it; asked again later, the late one counts once it shows it and the last answer says it is done; and at its next try the outbox first asks the relay that was sent it and gave no answer, and does not send it again when it has it. High-water marks (review of 9 Nov: every check read nine days from every relay, photos too, ~1.5–1.8 MB a minute): a relay that answered all it holds (EOSE) gets a mark per messaging key and the next read starts two days and ten minutes before it (the first read goes nine days back); one that does not answer in time, or whose pages do not end, gets none; a wrap not expected three times in a session is not opened a fourth, until `retry()`; one that holds more than the limit is asked for the older ones page by page, and every message comes; a wrap not expected yet comes back as deferred, with its date, and a floor makes the next read start before it.
- `relay_live_test.mjs` — the same layer against real public relays (the default list in `app/relay.js`, or `RELAYS=wss://…,wss://…`). Needs only Node 22 and four files of `app/`: `node tests/relay_live_test.mjs`. It checks each relay alone (takes a gift-wrapped event and gives it back), then the whole round, and passes if the round works through at least two relays. Not run from the build container (it cannot reach public relays). Passed on 5 Nov 2026 from a home network: the round took 23.2 s; alone, 3 of the 5 relays then listed worked (`wss://nos.lol`, `wss://relay.primal.net`, `wss://nostr.mom`) and the request came through all three; `wss://relay.damus.io` and `wss://relay.0xchat.com` gave "could not connect" from that network. The default list in `app/relay.js` is now those three.

- `requests_test.mjs` — requests without pasting a token: the app in Chromium against the local mint and three local test relays from `nostr_relay.mjs` (one refuses every event; the app is pointed at them with `localStorage['vetlock.relays']`). - `autosend_test.mjs` — the donor's locked donation goes to Streetcat by itself (8 Nov: a donation already paid is not sent by hand a second time), in the three apps against the local mint and local relays (7431/7432; 7433 down until the third case). - `handover_test.mjs` — in person, against the local mint and two local test relays: the donor's app shows a locked donation as an animated QR (numbered parts, changing by itself); the QR on screen decodes back with the app's own `jsqr.min.js`. - `signed_test.mjs` — campaigns signed by Streetcat (local mint, no relay). A new campaign's link carries a BIP-340 signature; the donor's page says "signed by Streetcat" and takes the donation. A link with its clinic key or its deadline changed says its signature does not match, greys out the payment and makes no call to the mint (no swap, no invoice); a field the signature does not cover is dropped. An unsigned link takes no donation either (review of 9 Nov: anyone can take the signature off a link they changed): with its signature taken off, empty or null, alone or with the Partner, the mint, the deadline or the purpose changed, it says so in red, greys out the three ways to pay and calls no mint by any route (ecash, Lightning, a Cashu wallet); a receipt of a donation made through a link from before links were signed (locked here in Node, its deadline 6 s away) still takes its sats back. The app pins Streetcat's published key (`STREETCAT_KEYS`, one line in `app/core.js`), and the test checks it is exactly that key; the test pins its own Streetcat key next to it by hand. A link naming any other key, signed with that key (a valid signature) or not signed, says in red "This link is not from Streetcat's published key. Do not donate through it.", never "signed by Streetcat", greys out the payment and makes no call to the mint; Streetcat's own page will not make such a campaign. Home signs a campaign made before when the browser holds its Streetcat key, and a browser without the key cannot make a campaign for it. `SHOT_DIR=dir` saves the donor's view of a signed, an unsigned, a broken and an unpublished-key link (`sg1`–`sg4`).
- `trust_test.mjs` — who is Streetcat for the partner and for a volunteer (review of 9 Nov, S1), against the local mint, no relay: a request from a key that is not Streetcat's published one (valid for `core.js`) opened by link says so in red, cannot be confirmed, sends no "received" back and is listed as not valid; the same request from the pinned key can be confirmed; a volunteer's phone refuses a donation handed over under another key and takes the pinned key's. The relay path is not covered. `node tests/trust_test.mjs`.
- `ledger_nostr_test.mjs` — the ledger published by Nostr, against the local mint and two local test relays (made-up keys; nothing goes to a public relay). Home's "publish ledger" sends the campaign's ledger v2 as one replaceable event (kind 30078, `d` = the campaign's id, a hash of its name, mint, keys and deadline), signed with the ledger key derived from the campaign's Streetcat key, and the status link carries `n=<id>`. `status.html` fetches the newest event, checks its signer and its campaign, and counts every donation at the mint. The campaign's announcement to donors, made with the campaign, is an event of its own (`d` = "announce:" and the id): it never replaces the ledger. Newer events under the same id signed by another key, or naming another campaign, are ignored. Publishing again replaces the ledger. With no relay it falls back to `l=` (the ledger's file), and says so; with neither, that the ledger was not found. A ledger too large for a relay is published with what fits (the donations something was paid from, then the largest) and says how many and how much are left out; a small one is published whole (independent review, 11 Nov).
- `wallet_test.mjs` — paying from a Cashu wallet (NUT-18, experimental), against the local mint and two local test relays. The donor's page shows a plain payment request (`creqA`: unit sat, the campaign's mint only, no lock in it, a description naming the campaign, single use), with "open in wallet" carrying that same request as a `cashu:` link (9 Nov; and the amount chosen is said on both ways to pay, and carried as chosen even when Pay with ecash is tapped 120 ms after a preset, while its digits still flip), and a Nostr transport (NIP-17) to an nprofile: a key made for this donation and kept with it, and the app's relays (the nprofile encoding is checked against NIP-19's example). A "wallet" in Node pays it as cashu.me does, with the NUT-18 payload in a NIP-17 message. Plain ecash is locked on arrival into the campaign's lock with the refund key kept for that request, and the wallet's ecash is spent at the mint. A payment made while the page was closed is picked up when it opens again. Ecash already locked to other keys (as a wallet applying only a lock's main key would make) is refused with the reason, and the request stays open; ecash already carrying exactly the campaign's lock is taken as it is; a token pasted by hand is locked the same way; ecash from another mint is not taken.
- `csp_test.mjs` — the browser security policy in `app/vercel.json`. The pages are served by the test's own static server on port 8090 with the headers Vercel sends (plus, for this test only, the local mint and relays in `connect-src`), and every screen of every role is opened, a donation locked, its card drawn, the scanner loaded and the service worker registered, and the status page checks a donation at the mint, while every `securitypolicyviolation` is recorded: none is allowed. It also checks that the pages keep no inline script or inline event handler (their code is in `app/index.js` and `app/status.js`, so the policy needs no hashes), that `vercel.json` carries every directive as decided, and that an inline script injected into the page does not run. The cat recognition runs under the policy too (its worker, the WebAssembly and both models, on a photo drawn in the page): it needs `'wasm-unsafe-eval'`, and `'unsafe-eval'` stays out; used once, the service worker has kept its files. Served without that word, its worker's WebAssembly is refused, so the policy is in force inside the worker as well (a worker gets the policy sent with its own file). That refusal is wanted and not counted: it is told apart by its worker (`catid-worker.js?strict`), not by time, since the console can report it a moment after its check (once, under load, it was counted against the next one).
- `receipt_test.mjs` — the donor's private recovery receipt, version 1 (no relay). After locking, "save private receipt" asks for a download of a PNG named for the donation ("download requested"); the donor ticks the box and confirms ("confirmed"); opening the saved file checks it ("Backup verified"). The PNG has one `tEXt` chunk (`streetcat.recovery-receipt`) with the JSON version 1 (format, version, created, campaign, donation with its code, amount, keyset and token, refund key) and a check (the first 16 hex of the SHA-256 of the rest, canonical), and every text the page draws is recorded: the private key never is. A screenshot of it (the picture without its data), an edited copy and another donation's receipt are refused, each with its reason. With a password (10 characters or more) the key is sealed (PBKDF2-SHA256, AES-GCM) and is in the file in no form; opening it needs the password. In a browser that never had the key (time zone Europe/Madrid), "Take my sats back" reads the file: what the receipt says and, apart, what the mint says, the refund date in UTC and local time, "Refund not available yet", and the most that can come back by Lightning or as ecash. A receipt made before version 1 (JSON) still opens, "no integrity check".
- `refund_test.mjs` — refunds read from receipts in browsers that never held their keys: a campaign whose deadline is 40 s away (keys made here), four donations. - `payout_test.mjs` — what Streetcat releases goes straight to its Lightning address (set once in Keys, behind the long button "Lightning address", since 9 Nov; in Home before), against the local mint and a local Lightning address server (LUD-16) whose invoices are the local mint's.
