# Tests

All tests run against a local Nutshell mint with a fake Lightning backend (no real money):

```
pip install cashu
MINT_BACKEND_BOLT11_SAT=FakeWallet MINT_PRIVATE_KEY=test MINT_DATABASE=./data/mint FAKEWALLET_BRR=TRUE MINT_INPUT_FEE_PPK=0 \
  python3 -m cashu.mint --port 3338 --host 127.0.0.1
```

On Python 3.13, `pip install cashu` (0.21.0) needs a hand: install its dependencies with `breez-sdk-spark==0.18.0`, `limits<4` and `marshmallow<4`, a `coincurve` 21 wheel, then `bip32` and `cashu` with `--no-deps`.

- `library_test.mjs` — the flow with cashu-ts only (`npm i @cashu/cashu-ts && node tests/library_test.mjs`).
- `browser_test.mjs` — the real page in Chromium, three parties with separate storage (`python3 -m http.server 8080 --directory app`, then `node tests/browser_test.mjs`; needs `playwright` and a `tokens.json` with two plain tokens from the local mint, see the top of the file).
- `status_test.mjs` — the status page: four real donations through `index.html` (one released, one left locked, one refunded, one left past its deadline) and one forged ledger entry, then `status.html` must report each from the mint alone. Then, in the donor's own browser, the page must list those four donations by itself and turn them into ledgers that read back the same. Same server as above; it mints its own fake ecash.
- `lightning_test.mjs` — donating with Lightning: the mint check on a new campaign, an invoice paid and minted straight into the lock, a reload between payment and minting (the mint call is blocked, then the page reloads), the mint's answer lost after it minted (the page gets the ecash back with NUT-09 restore), a link with a bad deadline, release with its answer lost (restored at once; and once more with restore blocked too, finished when the page is reopened), a refund paid to a Lightning invoice, a too-large invoice refused before anything moves, and a closed campaign. The fake Lightning backend pays the mint's own invoices, so no wallet is needed.

- `keys_test.mjs` — keys are never lost: a clinic that makes a new key after donations were locked to the old one still certifies them (the old key is kept); a browser holding another clinic key says which keys the token is locked to and does not sign; importing an export keeps the keys that browser had; the Streetcat tab of a browser without the Streetcat key stops before asking the mint; a plain token is refused with a clear message; and a new key that cannot be saved changes nothing.

- `release_test.mjs` — Streetcat releases only what the clinic really certified: a token with one proof unsigned ("Partly signed (2 of 3) — not certified") or signed with another key ("Signed with a key that is not MOCHI's clinic key") is refused before anything is sent to the mint; a part the donor already took back after the deadline is left out of the release; the clinic can still certify after the deadline, with a warning; and the status page counts each proof once, however many ledger entries list it (a part of a donation, the donation, and its certified copy). Once certified or released, the button says so in its screen's colour ("✓ Certified" in the clinic's blue, "✓ Released" in Streetcat's green) and cannot be pressed again, and the page buzzes (counted through `navigator.vibrate`); "release another token" empties the box and brings the button back; the same token pasted again says "✓ Already released" before anything is pressed, with no swap sent.
- `offline_test.mjs` — certifying without coverage: the clinic opens the app once with a connection, then its server is switched off and the browser goes offline. The app must still open from its service worker (`app/sw.js`), with its font, read the donation with the mint's keys kept from last time, and certify it ("Signed without a connection"); back online, Streetcat releases it. The cat recognition, got ahead of time with Offline setup's button (without starting it), must load offline from the phone and give, for a drawn photo, the numbers Streetcat's phone gives; a donor's phone, which never asked for it, must keep none of its 121 MB.
- `sw_test.mjs` — the service worker's version: `app/sw.js`'s BUILD must be the hash of the files it keeps, of itself and of `vercel.json` (its headers stay with each version's cached responses; `tools/stamp-sw.mjs`); fails when a file changed and the stamp was not run, or a file it keeps is missing. No browser.
- `swupdate_test.mjs` — a new version as a phone gets it (review of 9 Nov), on a copy of the app served on port 8096 with the service worker on: the first version is taken at once; version 2 is published and the app, just opened with nothing under way, opens again in it, every file from one cache filled whole, and Keys says its version (`Version <stamp>`); offline it still opens; version 3 is published while a payment waits for the mint: the app stays on version 2, and takes version 3 once nothing is under way, back in front; version 4, with one of its files missing, is never used and leaves no cache behind. Then, as every phone that has the app gets this version: the service worker before it (`sw-v6.fixture.js`, network first, its copy in `streetcat-app-v6`) serves the app on port 8097; this version is published over it, and the page takes the new worker and opens again in it, every file from its own cache, the old copy deleted; offline it opens as this version.

- `relay_test.mjs` — `app/relay.js` (requests and answers by Nostr relay) against three local test relays from `nostr_relay.mjs` (one refuses every event); needs Node 22 and `npm i ws` (for the test relays only), no mint. Streetcat sends a request and two relays confirm it; the clinic receives it once; its receipt and certified answer come back; an answer that comes before its request is known in that browser is not dropped, and comes (once) when the request is there; a request or an answer from a key that is not the campaign's is dropped, and so is a message for another clinic; with every relay down the message waits in the outbox and goes out when they are back; and the relays hold nothing readable (no cat, campaign, spending key or proof, and every wrap is signed by a throwaway key); the outbox keeps a message's copy only while it waits (once sent, only how it went, the last 300), cuts down an outbox from before at its next save, says so when the phone has no room left (`NO_ROOM`), and keeps a message added while it is sending (it was overwritten with the list read first). Relays slow to confirm (`nostr_relay.mjs` options `okDelay`, `storeDelay`, `mute`; 8 Nov, nostr.mom confirmed half a minute late and nos.lol never): one that keeps a message but confirms late counts as having it (asked by its id), one that has not kept it yet or never answers does not, one that answered no is believed, one not reached was never sent it; asked again later, the late one counts once it shows it and the last answer says it is done; and at its next try the outbox first asks the relay that was sent it and gave no answer, and does not send it again when it has it. High-water marks (review of 9 Nov: every check read nine days from every relay, photos too, ~1.5–1.8 MB a minute): a relay that answered all it holds (EOSE) gets a mark per messaging key and the next read starts two days and ten minutes before it (the first read goes nine days back); one that does not answer in time, or sends as many events as the limit, gets none; a wrap not expected yet comes back as deferred, with its date, and a floor makes the next read start before it.
- `relay_live_test.mjs` — the same layer against real public relays (the default list in `app/relay.js`, or `RELAYS=wss://…,wss://…`). It checks each relay alone (takes a gift-wrapped event and gives it back), then the whole round, and passes if the round works through at least two relays. Passed on 5 Nov 2026 from StreetCat's Mac, on his home network: the round took 23.2 s; alone, 3 of the 5 relays then listed worked (`wss://nos.lol`, `wss://relay.primal.net`, `wss://nostr.mom`) and the request came through all three; `wss://relay.damus.io` and `wss://relay.0xchat.com` gave "could not connect" from that network. The default list in `app/relay.js` is now those three.

- `ledger_nostr_test.mjs` — the ledger published by Nostr, against the local mint and two local test relays (made-up keys; nothing goes to a public relay). Home's "publish ledger" sends the campaign's ledger v2 as one replaceable event (kind 30078, `d` = the campaign's id, a hash of its name, mint, keys and deadline), signed with the ledger key derived from the campaign's Streetcat key, and the status link carries `n=<id>`. `status.html` fetches the newest event, checks its signer and its campaign, and counts every donation at the mint. The campaign's announcement to donors, made with the campaign, is an event of its own (`d` = "announce:" and the id): it never replaces the ledger. Newer events under the same id signed by another key, or naming another campaign, are ignored. Publishing again replaces the ledger. With no relay it falls back to `l=` (the ledger's file), and says so; with neither, that the ledger was not found.

- `csp_test.mjs` — the browser security policy in `app/vercel.json`. The pages are served by the test's own static server on port 8090 with the headers Vercel sends (plus, for this test only, the local mint and relays in `connect-src`), and every screen of every role is opened, a donation locked, its card drawn, the scanner loaded and the service worker registered, and the status page checks a donation at the mint, while every `securitypolicyviolation` is recorded: none is allowed. It also checks that the pages keep no inline script or inline event handler (their code is in `app/index.js` and `app/status.js`, so the policy needs no hashes), that `vercel.json` carries every directive as decided, and that an inline script injected into the page does not run. The cat recognition runs under the policy too (its worker, the WebAssembly and both models, on a photo drawn in the page): it needs `'wasm-unsafe-eval'`, and `'unsafe-eval'` stays out; used once, the service worker has kept its files. Served without that word, its worker's WebAssembly is refused, so the policy is in force inside the worker as well (a worker gets the policy sent with its own file). That refusal is wanted and not counted: it is told apart by its worker (`catid-worker.js?strict`), not by time, since the console can report it a moment after its check (once, under load, it was counted against the next one).
